Q1: 你在简历中提到负责“智能文问数”和“AI分析师”，请问你是如何优化Agent的意图识别准确率的？
考察点： 对RAG（检索增强生成）、Prompt Engineering、以及语义匹配技术的理解。

参考回答思路：
问题背景： 在金融场景下，用户提问往往很模糊（例如“看下那个涨得好的票”），直接丢给大模型容易产生幻觉。
解决方案（分层处理）：
结合我所做的智能SQL生成：
使用 bge-m3 模型将用户问题和数据库的元数据（表名、字段、描述）都转化为向量，存入 pgvector，利用 HNSW 索引进行高效的语义相似度搜索；
问题：
使用单一的向量检索在处理精确匹配时的不足。例如，用户问“查询股票代码为 '600519'的财报”，向量检索可能会因为语义相似而召回“贵州茅台”、“财务报表”等，但可能漏掉精确的表名 stock_financial_report 或字段 stock_code。
后续：
1、稠密向量检索：通过余弦距离 (<=>) 排序获取top-N；
2、利用 PostgreSQL 内置的全文检索FTS能力：使用zhparser对表名、字段名和描述进行分词，对数据表、描述和文档进行权重设计并生成GIN索引tsvector，确保能精确匹配到‘600519’这类代码或特定术语；
3、融合策略 (Reciprocal Rank Fusion, RRF): 算法来合并两套检索结果。它会给在两种检索方式中都排名靠前的结果赋予更高的综合分数，从而兼顾语义和相关性。
llm 重排序：将 RRF 筛选出的 Top-K 个表/字段，连同它们的 DDL 信息一起交给 LLM 进行最终的重排序和确认；
Prompting：加入数据库方言和少量示例；
后处理： 增加了一层校验逻辑，sqlglot对sql进行校验，判断表及字段正确性，仅执行select语句，追加limit限制，同时由数据库账号权限保证数据安全。

回答：
痛点：

Q3: 如果涉及到高并发的任务处理，Java线程池你是如何配置的？
考察点： ThreadPoolExecutor 参数配置、拒绝策略、OOM风险。

参考回答思路：
核心参数： 我不会直接使用 Executors 创建线程池，而是手动创建 ThreadPoolExecutor/ThreadPoolTaskExecutor，明确指定核心线程数、最大线程数、空闲时间和阻塞队列。
场景区分：
如果是CPU密集型任务（如代码静态分析），线程数设置为 N_cpu + 1。
如果是IO密集型任务（如调用API、读写数据库），线程数会设置得大一些，比如 2 \* N_cpu 或更多。
队列选择： 我会根据业务场景选择 LinkedBlockingQueue（无界，需小心OOM）或 ArrayBlockingQueue（有界，更安全）。
拒绝策略： 在金融场景下，我会自定义拒绝策略，比如将任务持久化到数据库或Redis中，稍后重试，而不是直接丢弃（DiscardPolicy）。

Q4: 请简述一下JVM的垃圾回收机制，以及你在线上遇到过OOM（内存溢出）吗？如何排查？
考察点： JVM调优、故障排查能力。

参考回答思路：
GC机制：
堆内存结构：新生代：包括 Eden 区和两个 Survivor 区。大部分对象在 Eden 区分配，经过多次 Minor GC；后存活的对象晋升到老年代；老年代：存放生命周期较长的对象，使用标记-整理算法进行回收；
默认堆内存：1/64-1/4；
引用计数 + 可达性 判断是否可回收；
分代收集
jdk8默认Parallel GC：新生代和老年代；Minor GC 回收整个新生代，Full GC 回收整个堆；停顿时间不可预测；
11默认G1：每个 Region 可以动态地充当 Eden、Survivor 或 Old 区，新生代复制，老年代标记整理；
-Xms2g -Xmx4g -XX:+UseG1GC -XX:MaxGCPauseMillis
ZGC：低延迟，染色指针（Colored Pointers） + 读屏障（Load Barrier），实现几乎全程并发；高频交易和风控系统
OOM原因：
JVM 初始化内存小，业务使用了大量内存；或者不同 JVM 区域分配内存不合理；
内存泄露：某一个对象被频繁申请，不用了之后却没有被释放，导致内存耗尽；
内存溢出：申请的内存超出了 JVM 能提供的内存大小；
OOM排查步骤：
保留现场： 配置 -XX:+HeapDumpOnOutOfMemoryError 自动生成Dump文件。
分析工具： 使用 MAT (Memory Analyzer Tool) 或 JVisualVM 打开Dump文件。
定位原因： 查看是内存泄漏还是内存溢出。
解决： 修复代码逻辑或调整JVM参数（如 -Xmx）
元空间溢出，类信息、常量、静态变量、即时编译器编译后的代码等，动态扩展
虚拟机栈溢出：-Xss 设置栈的大小
堆内存溢出，溢出的原因一般由于 JVM 堆内存设置不合理或者内存泄漏导致，jmap -heap查看泄漏对象到 GC Roots 的引用链，JVM 运行时查看最耗费资源的对象，jmap -histo:live 15162 | more

Q5: 你是如何利用Redis优化量化成果查询的？遇到了缓存穿透或雪崩问题吗？
考察点： Redis实战经验、缓存一致性、高可用。

参考回答思路：
优化策略： 生成的量化数据存储于数据库，在查询时，根据项目-课题id将热点数据序列化后存入Redis；
数据结构： 根据数据类型选择结构，例如使用 Hash 存储对象，或使用 ZSet 处理排行榜类数据；
解决穿透： 对于查询不存在的数据，我会缓存一个空值（Null），并设置较短的过期时间，防止攻击穿透到数据库；
解决雪崩： 在设置过期时间时，我会在基础时间上加一个随机值（如10-20分钟），避免大量Key同时失效；
一致性： 采用“先更新数据库，再删除缓存”的策略（Cache-Aside Pattern），并配合消息队列异步保证最终一致性。
