# 状态流转

Spring StateMachine 管理复杂流转
如何保证：
规则约束：通过配置类（@EnableStateMachine）明确定义“状态（State）”、“事件（Event）”和“转换规则（Transition）”。只有符合预定义规则的流转才会被允许，从代码层面杜绝了非法状态跳转（例如：未支付的订单不能直接发货）。
守卫条件（Guard）：在状态流转前执行校验逻辑（如：检查账户余额是否充足），不满足条件则阻止流转。
动作执行（Action）：在状态进入、退出或转换时自动触发业务逻辑，将状态管理与业务代码解耦。
持久化：支持将状态机上下文持久化到数据库或 Redis，确保服务重启后状态不丢失。

# 幂等控制

金融场景下，网络抖动、用户重复点击、MQ 重复投递都可能导致重复扣款或下单。
核心方案：Token 令牌 + Redis 分布式锁 + 数据库唯一索引的组合拳。
如何保证：
接口层（防前端重复提交）：使用 Token 机制。用户提交表单前先获取唯一 Token（存入 Redis），提交时携带 Token，后端验证后立即删除。结合 Spring AOP 可以无侵入地拦截所有需要幂等的接口。
服务层（防并发/重试）：使用 Redis 分布式锁。以业务流水号（如订单号）为 Key，通过 SETNX 原子命令抢占执行权，确保同一时刻只有一个线程在处理该业务。
数据层（最终兜底）：使用 数据库唯一索引。在核心业务表（如支付流水表）上建立联合唯一索引，即使上层防线被突破，数据库也能从物理上拒绝重复数据的插入。

# 数据一致性

金融交易对数据准确性要求极高，Spring Boot 提供了从事务管理到分布式协调的完整能力。
核心方案：Spring Transaction + 分布式事务框架 + 对账补偿。
如何保证：
本地事务：使用 @Transactional 注解保证单库操作的原子性（ACID），确保扣款和记账要么同时成功，要么同时回滚。
分布式事务：在微服务架构下，Spring Boot 可以集成 Seata 等框架，支持 TCC（Try-Confirm-Cancel） 或 Saga 模式，保证跨服务、跨库操作的数据最终一致性。
异步解耦与最终一致性：对于非实时强一致的场景，结合 RocketMQ/Kafka 消息队列。主流程成功后发送消息，下游服务异步消费。若消费失败，通过重试机制和死信队列保证消息最终被处理。
对账机制（兜底防线）：技术无法保证 100% 不出错，因此必须建立对账系统。通过定时任务比对上下游数据（如：支付渠道流水 vs 内部订单表），发现不一致数据后触发告警或自动补偿，这是金融系统的最后一道安全网。
